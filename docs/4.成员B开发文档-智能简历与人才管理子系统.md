## 1. 职责与边界

### 1.1 B 的范围

| 类型 | 工程 | 端口 | schema | 职责 |
|---|---|---:|---|---|
| Java | `resume-service` | 8084 | `recruit_resume` | 简历/人才主业务、解析编排、检索、匹配、去重、标签、规则、人才库 |
| Java | `file-service` | 8087 | `recruit_file` | 文件元数据、MinIO 对象存储、预签名、校验、下载 |
| Python | `ai-service` | 9010 | `recruit_ai` | LLM/ASR/Embedding 编排、任务、Prompt、降级、审计、人工复核 |
| Python | `ai-worker` | 8001 | 无业务表 | BGE Embedding、FunASR 流式 ASR（供 C 的在线面试） |
| Python | `mineru-worker` | 8002 | 无业务表 | MinerU 文档解析（PDF/Word/图片） |

- **3 个 schema**：`recruit_resume`（14 业务表 + 2 公共表）、`recruit_file`（1 + 2）、`recruit_ai`（8 + 2）。
- **ES**：`resume_vec` 索引，512 维、HNSW、IK、BM25 + kNN + RRF。
- **B 兼任**：AI 底座与 GPU 节点负责人（vLLM / FunASR / MinerU / ES 部署与压测）。

### 1.2 与 A / C 的边界

| 对方 | 边界 |
|---|---|
| A（gateway / auth / interview / notify） | A 提供登录、JWT、权限码、网关、通知消费；B **不实现**登录/鉴权/通知，只信任网关注入的用户上下文并发布事件 |
| C（room-service + 前端） | B 提供 FunASR WSS、BGE embedding、文件预签名能力；B **不实现** WebRTC/录制/房间业务 |
| interview 域 | `job` / `application` 归 A；B 只通过 `job.published` / `job.updated` 事件维护 `job_snapshot`，不跨库 JOIN |
| room 域 | `room.finished` / `recording.completed` 由 C 发布，B 消费用于纪要/评分/画像 |
| 前端 | 归 C；B 只提供 API/OpenAPI，不写 Vue 页面 |

### 1.3 数据所有权

- 只能写自己的 schema：`recruit_resume` / `recruit_file` / `recruit_ai`。
- 跨服务只传 ID + 必要快照，**禁止跨库 JOIN / 跨库写**。
- `person` 归 `resume-service`；interview/room 只存 `person_id` + 姓名快照。
- AI 输出一律为 **草稿**，人工确认后才写入正式业务状态。

```mermaid
flowchart TB

    FE --> GW[A 的 gateway]
    GW --> RSM[resume-service 8084]

    FIL -- 预签名直传 --> MINIO[(MinIO)]
    RSM -- 内部接口 --> FIL
    RSM -- 解析任务/事件 --> MQ[(RabbitMQ)]

    RSM -- 分块文本 --> AIW[ai-worker 8001]
    AIW -- BGE 向量 --> RSM
    RSM -- bulk index --> ES[(Elasticsearch resume_vec)]

    RSM -- LLM 实体抽取/匹配 --> AIS
    AIS -- OpenAI 兼容 --> LLM[vLLM / 云端 / Ollama / Mock]

    AIS -. room.finished / recording.completed .- CROOM[C 的 room-service]
    AIS -. interview.result.submitted .- AITV[A 的 interview-service]
```

### 2.1 简历解析流水线（题目硬约束）

```
file-service 预签名上传
  → MinIO 原件
  → file_meta(OK)
  → resume-service 创建 person/resume/resume_parse_task + Outbox resume.received
  → mineru-worker 消费：下载原件 → MinerU → Markdown/表格/公式/图注 → 上传 MinIO
  → resume-service 分块（300~500 token；表格独立成块；标题路径前缀）
  → ai-worker BGE 批量向量化（512 维）
  → ES bulk 写入 resume_vec
  → ai-service LLM 实体抽取（Schema 校验）
  → resume.structured_json 入库；parse_status=SUCCESS
```

### 2.2 人岗匹配流水线

```
规则硬过滤（学历/年限/地点/技能/年龄按规则配置）
  → ES 混合召回 top50（BM25 text^2 + skills + kNN + RRF）
  → ai-service LLM 精排 top20（技能/经验/学历/稳定性/潜力，五维+证据）
  → final = 0.3 × 召回分 + 0.7 × LLM 分
  → match_result 缓存（job/resume/prompt/model 版本）
  → 前端展示评分理由、证据片段、缺口
```

### 2.3 查重/去重流水线

```
SHA256 文件级（同文件秒传/命中）
  → phone_hash 精确层
  → ES kNN 摘要向量相似层（阈值 0.92）
  → resume_merge_record(PENDING)
  → HR 人工确认合并 / 拒绝
  → person.merged_to、resume_version 保留旧版本
```

### 2.4 人才库

```
标签（AI/HR） → talent_profile 归档
  → 人才检索/二次挖掘
  → 跟进记录 + next_followup_at
  → talent.followup.due 提醒（延迟 MQ 或定时扫描）
  → AI 画像草稿（简历 + 面试表现）→ 人工复核
```

## 3. 服务拆解

### 3.1 file-service（Java，8087）

**职责**：所有对象存储操作的唯一入口。

- `file_meta`：`file_key`、`bucket`、`object_key`、`sha256`、`mime`、`size`、`biz_type`、`biz_id`、`status`（UPLOADING/OK/REJECTED/DELETED）。
- 预签名上传/完成/分片；下载 URL（10 分钟）；MIME/大小校验（简历 ≤20MB，录像 ≤500MB，按 `biz_type`）；SHA-256 秒传；上传审计。
- 桶 `recruit` 私有；对象路径由 file-service 统一生成。
- **对象存储边界（已裁决）**：`resume-service` 不直接依赖 MinIO，所有读写走 file-service 内部接口。

**对外端点**：

| 方法 | 路径 | 权限 |
|---|---|---|
| POST | `/api/file/presign/upload` | 登录 |
| POST | `/api/file/complete` | 登录 |
| POST | `/api/file/multipart/**` | 登录 |
| GET | `/api/file/{id}` | 登录 |
| GET | `/api/file/{id}/url` | 登录 / `file:download` |

**内部端点**（`X-Internal-Token` + 网关屏蔽）：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/internal/files/register` | 登记已上传对象 |
| POST | `/internal/files/presign/upload` | 服务间获取上传 URL |
| POST | `/internal/files/presign/download` | 服务间获取下载 URL |
| GET | `/internal/files/{id}/meta` | 查询元数据 |
| POST | `/internal/files/{id}/complete` | 确认上传完成 |

**关键约束**：

- `file_key`、`object_key` 唯一；`sha256` 普通索引（用于秒传/查重）。
- `status` 只能由 UPLOADING → OK/REJECTED；下载只允许 OK。
- 预签名 TTL 固定 10 分钟，下载审计。

### 3.2 resume-service（Java，8084）

**职责**：简历与人才域的核心业务。

**表**（`recruit_resume`）：

| 表 | 关键约束 |
|---|---|
| `person` | `user_id` 唯一可空；`phone_hash` 索引；`merged_to`；`status` |
| `resume` | `resume_no` 唯一；`sha256` 唯一；`(person_id)` 索引；`parse_status` |
| `resume_version` | `(resume_id, version_no)` 唯一；parser/model/prompt 版本留痕 |
| `resume_parse_task` | `task_no` 唯一；`ai_task_no`；status/stage/progress；retry ≤3 |
| `resume_chunk` | `(resume_id, chunk_no)` 唯一；`chunk_type` TEXT/TABLE；`es_doc_id` |
| `candidate_skill` | `(person_id, skill_name)` 唯一；EXTRACTED/MANUAL |
| `tag` / `candidate_tag` | `tag_code` 唯一；`(person_id, tag_id)` 唯一；AI/HR |
| `talent_profile` | `person_id` 唯一；archive_level；summary；next_followup_at |
| `talent_followup` | `talent_profile_id`、HR、内容、下次跟进 |
| `screening_rule` | `job_id`、`rules_json`、match_mode、enabled、priority |
| `match_result` | `cache_key` 唯一；总分/召回/LLM/分项/证据/缺口 |
| `resume_merge_record` | source/target person、similarity、dedup_type、status |
| `job_snapshot` | `job_id` 主键；由事件维护；匹配只读本库 |
| `local_message` / `idempotent_consumption` | Outbox / 消费幂等 |

**模块**：

- `PersonService`、`ResumeService`、`ParseTaskService`、`ChunkService`、`SearchService`、`MatchService`、`DedupService`、`TagService`、`ScreeningRuleService`、`TalentService`、`PortraitService`。
- `EsResumeIndexService`：索引初始化、bulk、混合检索、`mysql-like` 兜底。
- `OutboxService` / `OutboxPublisher`；`JobSnapshotConsumer` 等。
- Feign：`AiServiceClient`、`FileServiceClient`；连接 2s/读 3s；traceId 透传。

**上传编排**：

1. 校验参数与文件元数据；
2. 创建/复用 `person`；
3. 创建 `resume`（sha256 判重）；
4. 创建 `resume_parse_task(PENDING)`；
5. 同事务写入 `local_message(resume.received)`；
6. 前端轮询 `parse-status`。

**解析阶段**：PARSE → CHUNK → EMBED → INDEX → SUCCESS；失败重试 ≤3 → DEAD；HR 可手动重试。

### 3.3 ai-service（Python/FastAPI，9010）

**职责**：所有 LLM/Embedding 编排的统一入口。

**表**（`recruit_ai`）：`ai_task`、`prompt_version`、`model_config`、`ai_result`、`ai_call_log`、`human_review`；可选 `agent_trace`、`ai_tool_audit`；公共表 `local_message`、`idempotent_consumption`。

**LLM 路由**：

```
vLLM（Qwen2.5-7B-Instruct-AWQ，主）
  → 云端 DeepSeek / 通义（备）
  → Ollama（无 GPU 档）
  → 模板 / Mock（开发/CI）
```

- 全部 OpenAI 兼容，切档只改 `base-url` + `model`。
- 超时、重试、顺序降级、熔断、配额、调用审计。
- `prompt_version` 从数据库读取；Prompt/模型变更走 PR + 固定评测集回归。
- 结构化输出：JSON Schema + Pydantic 二次校验；失败修复一次，再失败标记 FAILED。
- 简历/转写按不可信数据定界，防 Prompt Injection。
- 不推断年龄/性别/婚育等岗位无关属性。

**任务状态**：PENDING → RUNNING → SUCCESS / FAILED / DEAD；`progress`、`retry_count`、`error_msg`。

**能力**：

| 能力 | biz_type | 说明 |
|---|---|---|
| 简历实体抽取 | `RESUME_EXTRACT` | 教育/经历/技能/年限 + 置信度 + 证据 |
| 人岗匹配精排 | `MATCH` | 五维评分 + 证据 + 缺口 |
| 面试纪要 | `MINUTES` | 摘要/关键问答/风险/待确认 |
| 录播评分 | `ANSWER_SCORE` | 逐题相关性/结构/深度/表达/专业性 |
| 人才画像 | `PROFILE` | 简历 + 面试表现摘要 |
| 打标 | `TAG` | 职能/级别/技能/来源 |

### 3.4 ai-worker（Python，8001）

- `POST /api/v1/embed`：BGE `bge-small-zh-v1.5` 批量 embedding（512 维，批量 32~64）。
- `WS /ws/asr/{sessionId}`：FunASR 流式 ASR（Paraformer + VAD + 标点 + 热词），供 C 的在线面试。
- ASR 协议：`start` → 二进制 Int16LE PCM（16kHz/16bit/单声道，100~200ms/帧）→ `partial/final/error`。
- 单实例目标 ≥20 路；超限返回 `ASR_OVERLOAD`，主流程不阻断。
- `scope=asr` 短时 JWT 校验（由 C 的 room-service 签发）。
- 模式：`EMBED_MODE=mock|bge`、`ASR_MODE=mock|funasr`；Mock 用于无 GPU/无重依赖开发。

### 3.5 mineru-worker（Python，8002）

- 消费解析任务（RabbitMQ）或接受 `POST /parse`。
- 下载原件 → MinerU/magic-pdf → Markdown + 表格 + 公式 + 图注 → 上传 MinIO（经 file-service）。
- 回调/事件通知 resume-service；状态、进度、重试 ≤3、失败原因。
- 模式：`PARSER_MODE=mock|mineru`；Mock 用 PDFBox/Tika 或样例 Markdown，保证链路可跑。
- 与 ai-worker 分离部署，避免 MinerU 的 torch/paddle 依赖影响 ASR 服务。

### 4.2 ES `resume_vec` mapping

```json
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 0 },
  "mappings": {
    "properties": {
      "doc_type":      { "type": "keyword" },
      "resume_id":     { "type": "long" },
      "person_id":     { "type": "long" },
      "job_id":        { "type": "long" },
      "chunk_no":      { "type": "integer" },
      "chunk_type":    { "type": "keyword" },
      "section_path":  { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "content":       { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "skills":        { "type": "keyword" },
      "emb_model":     { "type": "keyword" },
      "embedding": {
        "type": "dense_vector",
        "dims": 512,
        "index": true,
        "similarity": "cosine",
        "index_options": { "type": "hnsw", "m": 16, "ef_construction": 200 }
      }
    }
  }
}
```

- 混合检索：`multi_match`（`content^1`、`skills^2`）+ `knn` + RRF。
- 升级 BGE-M3（1024 维）：新建索引 + 别名切换，不混存不同维度。
- `emb_model` 版本字段必须写入每条文档。
- ES 不可用：`SEARCH_MODE=mysql-like`，30 秒内切换（Nacos 配置）。

## 5. API 契约

### 5.1 通用约定

- 响应：`{"code":"0","message":"success","data":{},"traceId":"...","timestamp":...}`（沿用骨架 `0`，与 A 统一；文档 §3.1 的 `"OK"` 作为待统一项）。

- 每个非公开接口登记权限码；前端隐藏按钮不是安全边界。

## 7. 核心算法与规则

### 7.1 解析

- file-service 校验 MIME/大小/分片；对象入 MinIO。
- mineru-worker 下载原件，MinerU 输出 Markdown/表结构/公式/图注；产物经 file-service 上传。
- 解析任务状态：PENDING/RUNNING/SUCCESS/FAILED/DEAD；stage：PARSE/CHUNK/EMBED/INDEX；progress 0~100；重试 ≤3。

### 7.2 分块

- 300~500 token/块；按标题/语义切分。
- **表格整体独立成块**；超长表格按行分组并重复表头。
- 每块前缀注入标题路径：`[工作经历>腾讯>2019-2022]`。
- 工作经历尽量保持“公司+职位+时间+职责”同块。
- 写入 `resume_chunk`；`chunk_type=TEXT/TABLE`；`es_doc_id` 与 ES 文档对应。

### 7.3 Embedding 与 ES

- BGE `bge-small-zh-v1.5`，512 维，批量 32~64，CPU <20ms/条（目标）。
- `EMBED_MODE=mock` 时用确定性哈希生成 512 维，仅供开发。
- ES bulk 写入 `resume_vec`；每条文档带 `emb_model`。
- 检索参数/模型版本/人工反馈留痕，供 W13 评测复现。

### 7.4 混合检索

- BM25：`multi_match`（content、skills^2、section_path）+ IK。
- kNN：`embedding` topK。
- RRF 融合；召回 top50。
- ES 不可用 → `mysql-like`（SQL LIKE + 字段过滤），30 秒内切换。

### 7.5 人岗匹配

- 硬过滤：学历/年限/地点/技能（年龄按规则配置，注意 AI 纪律）；白名单操作符，≤1s。
- 召回：BM25 + kNN + RRF，top50。
- 精排：LLM top20，五维（技能/经验/学历/稳定性/潜力）+ 证据 + 缺口。
- 必备条件未命中 → 总分封顶。
- `final = 0.3 × recallScore + 0.7 × llmScore`。
- 缓存键：job 版本 + resume 版本 + prompt 版本 + model；`cache_key` 唯一。
- 结果可解释、可覆盖；人工确认后生效。

### 7.6 查重/去重

- SHA256 文件级：同文件直接命中，不新建 resume。
- `phone_hash` 精确层：同手机号提示合并。
- ES kNN 摘要向量层：阈值 0.92；正负样本定标。
- 只提示，人工确认合并；`resume_merge_record` PENDING → CONFIRMED/REJECTED。
- 保留 `resume_version`；`person.merged_to` 指向主档案。

### 7.7 标签

- `tag`：职能/级别/技能/来源等维度。
- `candidate_tag`：AI/HR、置信度、操作人。
- AI 打标（`TAG`）产出草稿；HR 可覆盖。

### 7.8 筛选规则

- `screening_rule.rules_json`：`[{field,op,value}]`。
- 字段：学历、工作年限、城市、技能（年龄按规则配置）。
- 操作符白名单：`EQ/NE/GT/GTE/LT/LTE/IN/NOT_IN/CONTAINS`。
- `match_mode`：RECALL_ONLY（只召回）/ HYBRID（召回 + LLM 精排）。

### 7.9 人才库与画像

- `talent_profile`：归档等级 SILVER/GOLD/PLATINUM、摘要、面试历史、负责人、下次跟进。
- `talent_followup`：HR、内容、下次跟进时间。
- 跟进提醒：`talent.followup.due`；MQ 延迟插件未启用时用定时扫描。
- AI 画像：简历 + 面试表现 → 草稿 → 人工确认写 `summary`；不推断敏感属性。

### 7.10 AI 路由与审计

- 四级路由 + Mock；OpenAI 兼容；切档只改 base-url + model。
- Prompt 版本、JSON Schema、Pydantic 二次校验、失败修复一次。
- `ai_call_log`：traceId、taskNo、capability、provider/model、prompt、tokens、latency、status、degraded_to。
- 配额/预算熔断；日志脱敏；不记录简历全文/密钥。

|---|---|---|

```bash
# 默认：Mock + 仅 MySQL
AI_MODE=mock PARSER_MODE=mock EMBED_MODE=mock ASR_MODE=mock \
SEARCH_MODE=mysql-like MQ_ENABLED=false STORAGE_MODE=local

# 切云端 LLM
AI_MODE=cloud CLOUD_BASE_URL=https://api.deepseek.com/v1 CLOUD_API_KEY=...

# 切本地 vLLM
AI_MODE=vllm VLLM_BASE_URL=http://127.0.0.1:8000/v1 VLLM_MODEL=qwen2.5-7b

# 切真实解析/向量/ES
PARSER_MODE=mineru EMBED_MODE=bge SEARCH_MODE=es ES_URI=http://127.0.0.1:9200
```

### 12.1 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| MinerU 依赖重、镜像大、图片 OCR 复杂 | 解析链路阻塞 | 先 mock；W1 spike；独立容器 |
| FunASR/GPU 显存与并发 | 字幕容量不达标 | BGE CPU 可跑；FunASR 需 GPU；20 路契约 |
| ES IK/HNSW 初始化复杂 | 向量检索不可用 | 自定义镜像/脚本；mysql-like 兜底 |
| RabbitMQ 延迟插件未启用 | 跟进提醒/过期延迟 | 定时扫描兜底 |
| 端点/事件契约漂移 | 跨服务联调失败 | 本文为 B 基线；变更先改文档/OpenAPI |
| 全量 B 工作量大 | 延期 | P0 主线优先；FunASR/异步/画像后置 |
| 本地 AI/基础设施未定 | 无法真实联调 | Mock + 三档基础设施；W1 spike 后定档 |
| 数据隐私 | 简历敏感信息 | 最小权限、脱敏日志、不推断敏感属性 |

### 12.2 待确认

1. 老师对 Flyway/ES IK/MinIO 桶初始化的意见（第 7 条）。
2. 本地 AI 档位：Mock / 云 API / vLLM / Ollama。
3. 本地基础设施：full / slim / minimal。
4. 与 A 的成功码、用户头、事件命名最终对齐。
5. 与 C 的 ASR 端口、Nginx rewrite、`scope=asr` 令牌联调。
6. 人才画像是否保留（原文档列为待评审裁剪项）。
7. 年龄字段的筛选规则与“AI 不推断敏感属性”的边界。
